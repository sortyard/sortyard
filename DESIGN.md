**Failure shape this produces** (all from the last 10 days of records):
1. State lives in ≥5 places (Plane, meta-harness registers, control-plane SQLite, GitHub PRs, Juno's memory) and they drift. Stale-fact failures are a named, recurring defect class.
2. Policy lives in prose. Pickup order, lane caps, merge gate, hand-back semantics, eval absent-states — written in AGENTS.md / MEMORY.md / plan files, enforced (or not) by code in three repos. When code and prose diverge, nobody notices until a stall.

5. Extensions are files in a git repo edited by commit. Skills, workflows, archetypes are powerful — but there is no registry, no versioning contract, no enable/disable, no UI.

The reboot keeps every capability and every hard-won rule. It changes the *packaging and the locus of truth*: one installable system, domain objects instead of scattered files, policy as data, UI for operators, API for agents — with git retained where git is actually good (versioning definitions, review, audit).

## 1. First principles

1. **Advance only on observed state, never on self-report.** The existing rule, kept verbatim. Every state transition in the new system is driven by an observed fact (job exit, check result, PR merged, deploy healthy) recorded as an event with a timestamp. No component may assert a state it did not observe.
2. **The conductor is a state machine.** Joe, 2026-11-04: "It always has been — the conductor is just a state machine." So build it as one, explicitly: states, transitions, guards — inspectable, replayable, testable. Scheduling must be *derivable*: given the board state and the policies, anyone (UI, agent, auditor) can compute why item X was picked, why Y was not, and what happens next. Zero guesswork is a system property, not a reporting discipline.
3. **One source of truth per domain object.** Tasks, policies, lanes, workflows — each has exactly one authoritative store. Everything else is a projection (a view, a cache, an export) and is labelled as one. This kills the Plane↔register↔SQLite drift class by construction.
4. **Pipeline has no dependencies on deployment environments or third parties.** Replica checks (causal feature test, quality walks, adversary review) happen upstream in the builder's loop; live-product checks happen in the out-of-band Acceptance Test Lane. The pipeline itself: fake providers + own fast tests only. (Joe, 2026-11-03/04, fleet-wide.)
5. **Zero-difference environments.** The local replica *is* the deployment shape. The harness ships the replica tooling; a feature is not ready to push until it has been exercised causally in the replica.
6. **Process compliance is not quality.** Fewer gates on *how*, stronger executable checks on *what*. Every gate/eval defines its absent state ("could not run" ≠ "failed" — name what happens instead, never a silent wait).
7. **Template-first, archetype-driven.** A project is an instance of an archetype (today: `saas-product`, `infrastructure`). Fix the template, projects inherit. No verbatim forks.
8. **Humans steer at the outcome level; agents do the mechanics.** The operator's job in the UI: set intent, priorities, policies, budgets; approve the few irreversible/expensive things; judge shipped quality. Everything else — pickup, grooming, retry, merge mechanics, reporting — is the system's job, unattended.
9. **OSS-shaped from day one.** Clean install on a vanilla cluster, no NonceLogic-specific assumptions in the core (tailnet names, jump boxes, Plane instance, Juno). NonceLogic specifics live in *our deployment's configuration*, not in the package. If we can't `helm install` it on a fresh cluster in an afternoon, it's not done.
10. **Boring, finished technology over bespoke machinery.** Adopt the most finished thing that exists (Joe's standing rule); build only the differentiating machinery: the domain model, the conductor state machine, the context assembly, the eval/prioritization logic.

11. **No unbound agents.** An agent is never an assignee in the abstract. Every execution is bound (§3.7b) to a pinned workflow, an assembled and hashed context packet, exact skill versions, a model/budget policy, a named place (lane, cluster, worker image, isolated workdir, fresh mirror), and a verified dependency set — before the task is eligible to be claimed. If any element cannot be resolved, the task is not eligible and the Pickup Preview names the missing element. This is the direct negation of the tracker-agent model (assign a generic agent to an item and hope its setup matches the work), which this design rejects by name.
12. **Open by design; the community is the ideation engine.** The package is open source because its improvements are expected to come from people (and their agents) we will never meet, doing things we never thought of (§11). Small core, extension-first, agent-legible, contributions verified rather than trusted.

## 2. The product in one paragraph

**Harness (working name: keep "harness" — repo `harness` already exists; the meta-harness name dies)** is a Kubernetes-native control system for agent software factories. You declare *projects* (instances of *archetypes*), *workflows*, *policies* and *lanes*; agents and humans create *tasks*; a deterministic *conductor* schedules tasks through workflow stages executed by *harness workers* (agent CLIs in Jobs); *evals* judge outcomes on observed evidence; an *operator console* (the pane of glass) shows everything and controls everything; and every operation an agent needs is an API call. It installs with one Helm chart, stores its state in Postgres, its secrets in an external secrets store, and its definitions in both a database (live state) and git (versioned, reviewable definitions) — with a clear rule for which wins (§5.1).

## 3. Domain model — the logical objects

Everything Joe named, plus the objects the current system has implicitly. Each object: authoritative store, key fields, lifecycle/state machine, who can create/change it (human via UI, agent via API, system only).

### 3.1 Tenancy & installation
- **Installation** — one deployed harness instance. Config: cluster, namespaces, storage, ingress, auth provider (OIDC).
- **Workspace / Organisation** — tenancy boundary inside an installation (v1: single workspace is fine, but the field exists on every object from day one — retrofitting tenancy later is the classic rewrite trap, and the meta-harness declaration already carries a `tenant_scoped` property for this reason).

### 3.2 Projects & archetypes
- **Project** — a product being built. Fields: id, name, archetype ref, repos[] (each: URL, default branch, role — product / GTM / infra), tracker pointer (internal by default; external tracker optional, §8), delivery config ref, quality bar ref. Lifecycle: `discovery → active → maintain → archived`.
- **Archetype** (template) — a versioned bundle: default workflows, roles, contracts, skill slots, eval suites, replica definition, definition-of-done. Today there are two shipped archetypes (`saas-product`, `infrastructure`) plus two registered *candidate* archetypes (inception, opportunity-portfolio) — and the present reality is worse than “copy and drift”: instance scripts are copies with **no propagation mechanism at all**, and per meta-harness MANUAL.md, `templates/infrastructure/` cannot currently be emitted and validated at all. Projects in the reboot *pin* an archetype version and inherit updates explicitly (diff + accept in UI). Archetype changes are themselves tasks run through the system (dogfood rule). Project states in the source are `discovery / active / maintain / project-definition` (the draft v0's `archived` does not exist in `repos.yaml`).
- **Repo** — first-class, not a string in a YAML file: connection status, webhook health, runner pool, branch protection posture, last observed HEAD. The naming/topology lesson (codename vs product name silently breaking automation) is solved by explicit `role` + `aliases[]` on the Repo object.

### 3.3 Work
- **Task** — the unit of work. This absorbs today's Plane work item + meta-harness task block into ONE object. Fields: project, title, outcome statement (what, not how — no acceptance tests tacked on, per Joe's 2026-11-04 rule; verification lives in workflows/evals), spec/body, `depends_on[]`, `parent/children`, milestone ref, priority (see Prioritization), labels[], origin (`human | sensor | grooming | eval-finding | chain`), needs[] (capabilities/credentials the work requires — with the HARNESS-238 lesson baked in: a needs-blocked task still exists and is visible, it is simply not eligible), assignee lane, state. **State machine:** `backlog → todo (groomed/eligible-computable) → claimed → in_progress (per workflow stage) → in_review → merging → done`, with explicit side states: `blocked (reason required)`, `handed_back (reason + evidence required)`, `cancelled`. Hand-back is a *decision, not a defect* — a first-class transition with a mandatory reason, never a label hack.
- **Milestone** — ordered grouping of tasks; ordering inside a milestone is explicit (`sequence`), because pickup order reads it.
- **Sequence / Sequencing (see §3.3a)** — the recorded execution order of work. Not a container object like a bucket; a property of Tasks, Milestones, Workflows and Chains, governed by one SequencingPolicy per project. Fully defined in §3.3a.
- **Decision** — a first-class work type, implementing your no-tap doctrine: a question for the operator, a **recorded default**, and a `decide_by` time. The operator may answer (in the UI, or by comment via an integration); **silence past `decide_by` applies the default and closes the item unattended**. Decisions are how humans steer without ever being a step inside delivery — workflows never block on a person; they branch on a Decision object that always resolves.
- **Chain / Run** — one task's passage through a workflow: the ordered stage executions, each a **StageRun** (job ref, agent session ref, inputs packet hash, outputs, observed facts, cost, duration). Chains advance automatically; stalls are explicit objects (**Escalation**: reason in plain language, stall class, repair attempts) — formalising the current mh-chain rules in full: revision rounds cap at **four**; stall classes include repeated blocker with no substantive record change, twice-failed infrastructure, failed declared checks, and illegal dispatch; self-repair gets at most two attempts **per distinct defect (class + phase)**, a repair concluding “not dispatcher-side” ends after one attempt, and redeploy failure / repaired code not running within 15 minutes are also terminal conditions.

### 3.3a Sequencing — the order work actually runs in (replaces “temporal buckets”)

Prioritization answers *what matters most*. Sequencing answers *what runs next, after that* — and in this system the second answer must be just as derivable as the first (§1.2). Sequencing is not one field; it is the combination of five recorded orders, all visible in the Pickup Preview:

1. **Milestone sequence** — milestones run in an explicit order per project (your standing rule, 2026-10-29: pickup is milestone by milestone), and tasks carry an explicit `sequence` inside their milestone. Grooming owns keeping the *next* milestone sequenced ahead of the train; an unsequenced milestone behind a finished one is shaping debt, surfaced as such.
2. **Dependency order** — `depends_on` and parent/child gating: a task is sequenceable only when its dependencies are done and its parent is not in Backlog. Dependencies don't change a task's priority; they change its *position* — it cannot be claimed out of order, and the preview says exactly which dependency holds it.
3. **Workflow stage sequence** — inside a Chain, stages run in the workflow's declared order (Frame → Judge → Shape → Build → Verify; design → dual review → approval → build → verify), with parallelism only where the workflow declares stages independent. Stage sequencing is data in the Workflow object, never conductor improvisation.
4. **Claim sequence** — at each conductor pass, eligible tasks are ordered by the PrioritizationPolicy (§3.5: urgent → milestone sequence → priority tier → age / board sequence number) and claimed in that order until lane slots fill. A claimed task's slot is held through every phase including `merging`, so the sequence the preview showed is the sequence that actually executes — no silent reordering between preview and claim.
5. **Fairness / interleaving** — with multiple projects sharing lane capacity, a **SequencingPolicy** (per installation or per lane) states how claim sequences interleave: strict global order, per-project round-robin, or reserved slots per project (today's de facto model: per-project lane caps). Whichever is chosen, it is recorded policy, applied mechanically, and shown in the preview — never an emergent side effect of poll timing.

A **SequenceChange** is an auditable event: whenever a human (board drag, §6) or grooming reorders a milestone or a task's sequence, the change, its author and its reason are recorded, and the Pickup Preview re-derives from the new order immediately. There is no hidden queue anywhere in the system: if an order exists, it is one of these five, and it is written down.

*What sequencing is not:* it is not scheduling by wall-clock. Nothing in the claim path waits for a time window to open. Time-based constructs exist only where they genuinely belong — Decision `decide_by` deadlines, credential-pool cooldowns, sensor/eval cadences, and the retrospective ThroughputWindows of §3.8.

### 3.4 How work flows
- **Workflow** — a versioned, declarative stage graph (not a markdown table parsed by regex, which is how `dispatch` reads it today): stages[], each with role, executor type (`agent | deterministic`) — **there is deliberately no `human-gate` executor type**: humans act through Decision objects (§3.3), never as a blocking stage. Built-ins carry over today's real set: saas-product `feature` (whose actual stages are **Frame → Judge → Shape → Build → Verify** — the Judge stage, *should-this-exist before design*, is a distinctive current mechanism the reboot keeps consciously), `incident`, `release`, `support`; infrastructure `change`, `drift`, `incident`; plus `job` (one-off investigation — today's conductor `job` type) and the `design-first` chain (design → dual review → approval → build → verify). Workflows are data, editable in UI, stored versioned; a Chain pins the workflow version it started on (see §5.1 for what happens when that version is edited mid-chain).
- **Role / Persona** — who is asking at a stage: planner, implementer, reviewer, designer (the template roles today; infrastructure omits designer), plus the agentic-persona platform's C-suite personas as they land. (v0 also listed an “operator” role — invented; operators are users of the console, not workflow roles, and it has been dropped.) A role = system-prompt bundle + context allowlist policy + tool permissions + default model policy. Roles are objects, not folders.
- **Lane** — a concurrency + routing construct: max concurrent chains, eligible projects/workflows, host/cluster pool, heavy-job cap. The reboot must model **both** of today's cap systems (conductor slots and dispatcher lanes — values in §0) as Lane objects with an explicit `scope`, because they govern different loops. Lanes are tuned live from the Admin console. Today, changing a dispatcher cap means editing `delivery-train.yaml`, committing, and redeploying the control plane to rebundle `mh-projects.json`, and changing a conductor cap means a manual control-plane release (HARNESS-246) — both paths disappear.
- **Conductor** — the deterministic scheduler service. Not an object, but its *configuration* is: pickup policy ref, poll interval, claim lease duration, stall thresholds. Its decision log is an object (§3.8).

### 3.5 Prioritization
- **Priority** — not a single enum. The pickup order today is a strict **lexicographic** order: urgent first → milestone order → Plane priority → age (board sequence), over eligible items only (conductor-labelled Todo, parent not in Backlog — a Backlog parent releases nothing, including decisions — and `depends` satisfied). v1 keeps it lexicographic: a **PrioritizationPolicy** is an ordered list of keys (`urgent_flag`, `milestone_sequence`, `priority_tier`, `age`), tie-break roles only, per project or global. Weighted scoring / a `cost_of_delay` key (as floated in v0) would be a *change* to Joe's ordering and is flagged as such in §10, not smuggled in as a transcription. Two further mechanics are load-bearing and now explicit: **a slot stays occupied by any claimed item that is neither done nor blocked, whatever its phase, including `merging`** (the rule behind CPV2-574 / HARNESS-242 — stalled merges hold lanes), and the Pickup Preview's reason codes include `slot held: merging` and `held: parent in backlog`. The UI shows a *pickup preview*: "given current state, the next 10 claims will be these, in this order, for these reasons" — derivability (§1.2) made visible. Urgent bypasses lane caps and does not count against them (current rule, kept). Priority tiers: `urgent | high | normal | low`.
- **Grooming** — a system function, not a human chore (Joe, 2026-11-05: grooming is automated as a process step; a task counts as groomed only when schedulable from its recorded state alone). A **GroomingPass** is a scheduled/agent job that: turns findings into tasks, fills depends/priority/placement, orders milestones, and verifies pickup-eligibility — and files a defect when a project's eligible queue is empty while known work exists ("never an empty groomed queue"). Grooming's judgment work is **frontier-model only; a non-frontier run stops and reports the mismatch** (Joe, 2026-11-05) — recorded as a Policy on the pass, not a hope.

### 3.6 Policy
- **Policy** — the big unification. Today policies are prose in AGENTS.md. In the reboot, every enforceable rule is a Policy object: id, scope (global/project/workflow/stage), kind, parameters, enforcement (`refuse | warn | record`), absent-state behaviour (mandatory for eval gates), version, audit history. Kinds:
  - `merge_gate` — red never merges; absent checks = coverage gap (record + file ticket + merge on review/local proof); no force-merge ever. Review counts are **scoped by regime**, because today there are three: (a) *conductor product PRs* — exactly one harness verify/review, with fix-round handling as amended by k3s-harness #199 (v0's flat “1 fix round then backlog” predates #199; the exact post-#199 count is **unverified** — drive.py source is in no local checkout — and is flagged in §10 as a must-verify before build); (b) *design records / definition of done* — **two reviewers** against the `design_ref`; (c) *mh design chains* — **dual review** (correctness + usability, separate sessions). The Policy carries a `regime` field; any single flat number is a design error.
  - `pipeline_purity` — no stage in the delivery pipeline may declare a third-party or deployment-environment dependency; the workflow validator *refuses* such a workflow (prose rule → script refusal, the meta-harness tradition).
  - `replica_required` — build stages must attach replica adversary-review evidence before push.
  - `secrets` — secrets only via the secrets store, only into jobs that declare the need, never logged, never in definitions.
  - `model_budget` — per-key budgets (Joe, 2026-11-04: budgets live per API key, not in the product); model/effort selection per stage (see Context, §3.7).
  - `credential_pool` — subscription accounts as pooled resources: selection + failure isolation (least-burned picker, 5h cooldown on limit, max 3 requeues). The pool is not a lease and not a concurrency limiter (from the working pool design, promoted to policy + data).
  - `retention`, `runner` (no GitHub-hosted runners — estate/self-hosted only, Dependabot sole exception), `handback`, `stall`, `escalation`.
- Policies are changed in the Admin UI (with audit + optional git export), and the conductor/workers *read policy at decision time* — change a lane cap or a fix-round count and the next decision uses it. No redeploys for tuning. That is the "control, tunability and flexibility without losing any" requirement, made literal.

### 3.7 Agents, context, extensions
- **Agent / Worker** — an executor: harness type (`claude-code | codex | hermes | custom`), model policy, credential pool ref, tool set. Workers run as K8s Jobs, one stage per pod, no GitHub/tracker access by default, never push — they produce a branch/patch in a clone taken from a **repo mirror** (below). Kept from today, it's a good security shape.
- **Mirror** — workers clone from read-only mirrors on a shared volume; jobs never fetch private remotes. Mirror freshness is a recorded fact on every dispatch, and a stale mirror is a named failure mode (the J03 stale-seed-base incident). The reboot keeps Mirrors as objects (source, last-refresh, freshness) with a refresh service — v0 assumed repos simply exist in-cluster; they don't.
### 3.7b Execution Binding — the guarantee Plane's agents don't give (added v3)
An **ExecutionBinding** is the resolved, verified answer to the four questions Joe named (2026-11-06) as what makes a tracker-agent mode untrustworthy — *where will the agents do the work? what agents will do the work? do the agents have the information, skills and workflow in place? and can the work be throttled so one agent can't tank the host and kill other workstreams?* A binding is produced for a (task, stage) pair *before* the conductor may claim it:
- **Right workflow?** — workflow id + pinned version, stage, and role/persona for that stage. No binding, no “the agent will figure out the process.”
- **Right context?** — the ContextRecipe (§3.7) assembled into a packet, content-hashed, provenance/drift-checked, and goldfish-tested: the packet plus its referenced dossier/design record must be sufficient for a zero-context agent. The binding records the packet hash; the StageRun must run that exact packet.
- **Right skills?** — the exact Extension/Skill ids *and versions* the stage requires, confirmed installed and enabled for the project. A missing or version-drifted skill fails the binding by name.
- **Right place?** — lane, cluster/namespace, worker image + harness type (claude-code/codex/…), model + effort + per-key budget, credential-pool selection (or store refs), isolated workdir, repo mirror + its freshness fact, and — for build stages — the replica definition for the adversary review.
- **All dependencies brought to bear?** — `depends_on` tasks done *and their output artifacts attached* (by reference, materialised into the workdir before the agent starts, as mh attachments do today); parent not in Backlog; `design_ref` present and approved where the workflow requires it; `needs[]` discharged — integration contracts in place, secret refs resolvable (never values), estate preconditions evidenced (the HARNESS-274 rule: a production-flipping task is not eligible until the estate preconditions it assumes are named dependencies and discharged).
- **Bounded blast radius (the throttling guarantee)?** — every binding carries a **ResourceEnvelope**: CPU/memory requests *and limits* on the Job, a wall-clock deadline (expiry kills the Job), and a heavy/light classification. Admission is controlled at three stacked levels, all recorded policy: **lane caps** (per project), **per-project heavy caps** (one train cannot consume every heavy slot), and a **cluster heavy cap** with a **reserved rush slot** (rush is admitted first but *never preempts a running job*). Work that cannot be admitted is not launched and left to fight — it stays queued and eligible, with the Pickup Preview showing `throttled: heavy cap full` (the cap value itself is deployment-specific — 1 in code default, 2 in the local manifest, 4/train-3 in the dispatcher's header note for the D16s_v6 deployment) as its reason. This is what the current harness actually guarantees and the reboot keeps in spirit: Jobs are isolated (own pod, own workdir — the shared-workdir collision of 2026-09-26 is a named anti-pattern), think/shape stages free-run while build/verify/proof stages are heavy-capped (`HEAVY_STAGES` in mh.py). Proof-class sizing, stated accurately (the v3 text overstated this and the checker corrected it): the proof worker requests 2 CPU/4Gi (limits 4 CPU/6Gi) and its Docker sidecar requests 1 CPU/2Gi (limits 4 CPU/8Gi) — combined requests 3 CPU/6Gi, combined limits 8 CPU/14Gi. On the retired D8s_v6 with earlier limits that was most of a node, which is where the cap's reputation comes from; on today's D16s_v6 (16 vCPU/~64Gi) the limits are about half the node's CPU and a fifth of its RAM — still by far the heaviest class, still capped. Credential-pool *selection* bounds usage (least-burned picker over a 5h window, 5h cooling and max 3 requeues on a limit failure — the pool is selection + failure isolation, it is **not** a concurrency lease) while concurrency is bounded by the caps alone. The one-heavy-eval-per-host rule (§3.8) is today **policy in prose, not an enforced mechanism** — the reboot either enforces it in the Eval Runner or says so plainly; v4 records it as enforcement work in scope. A runaway agent therefore consumes at most its envelope and its deadline — it can fail its own task; it cannot starve the other trains. **One honesty correction on the control plane itself:** today it runs with only small requests and no PriorityClass/ResourceQuota protection — it is *not* reserved-capacity-isolated from worker Jobs. The reboot adds that as explicit design work (control-plane PriorityClass + reserved requests, worker LimitRange), it does not inherit it.
**Binding is a pre-claim gate, computed by the conductor on every pass and shown in the Pickup Preview.** An incomplete binding makes the task ineligible with a specific reason code — `unbound: no approved design_ref`, `unbound: skill <x>@<v> not installed`, `unbound: mirror stale`, `unbound: credential pool empty`, `unbound: dependency <task> has no artifact` — never a generic “not ready.” This generalises three mechanisms that already exist separately today: `dispatch`'s refusals, `task_ready` gating in plane_sync, and the `needs` gate (with the HARNESS-238 lesson kept: the task stays fully visible while unbound; it simply cannot be claimed).
**Contrast, stated plainly:** a tracker agent (Plane Agents: assign or @mention an agent built from a template + playbook + model + trigger; it “picks up context” inside the tracker) binds *none* of the above — the workflow is a playbook prompt, the context is whatever the workspace holds, the skills are the agent vendor's, the place is the vendor's runtime, task dependencies are links, not materialised inputs, and there is no resource envelope or admission control the operator owns — the agent runs as hard as it runs, wherever it runs, alongside everything else. That model is fine for triage and drafting; it is not a delivery mechanism. In this design, tracker-style agents may exist only as *Sensors/assistants* (filing, triaging, summarising) — they can create and comment on tasks, and they can never execute one. Execution is bound, or it does not happen.

### 3.7a The shipping leg and credential custody (added in v1 — v0's largest hole)
- **Integrator (`ship.py` successor)** — the fenced single writer that turns a proven delivery into a landed one: it requires a proof receipt `passed` for the exact (base, candidate) pair + verify approval of the exact head + a tree-identity assertion, then lands via the Git Data API recreating signed commits byte-exact, with a register checkpoint recording both heads. (The conductor line has a second, different integrator today: drive.py fetches commits via git bundle from the `mh-tools` pod and merges itself. The reboot unifies on the fenced model and says so explicitly.)
- **Where the GitHub write credential lives is a design decision, stated here, not an accident of the diagram:** today the cluster **deliberately holds no GitHub credential** — `ship.py` and `mirror_refresh.py` run operator-side because the only write credential is the user-connected connector credential on the agent side. The reboot preserves that posture by default: the Integrator runs as a component that receives the credential through the installation's configured custody (for NonceLogic: operator-side, as today; for OSS installs: a scoped GitHub App installed by the operator). Moving a long-lived GitHub write credential into the cluster is a security-posture change that requires Joe's explicit approval and is **not** assumed anywhere in this design.
- **Auth Broker (credential pool's other half)** — subscription credentials are a special custody class: the control plane brokers Codex device-flow and Claude `setup-token` grants interactively (a human approves in their own browser), and the resulting credentials live as 0600 files on a dedicated volume — **deliberately not in the secrets store and not as K8s Secrets, because the CLIs own the refresh lifecycle and write tokens back**. v0's blanket “secrets only via the secrets store; values never transit the API” is contradicted by the live system on purpose (the broker's paste-token endpoint exists by design). The reboot therefore models **CredentialCustody** explicitly per credential: `store | cli-owned-files | operator-side`, each with its own rules — instead of one blanket rule the real system already violates for good reasons.
- **Context Assembly** (the `dispatch` successor) — per stage, the system assembles the agent's context from an *allowlist* (project + workflow + role), not from retrieval over a vault (36% dead material is why). A **ContextRecipe** object defines, per project/worktype/role: which domain objects, documents and skills are included, in what order, with token budget. Every StageRun records the exact packet (hash + content ref) it received — reproducibility and the goldfish test (a zero-context agent must be able to execute from the packet + referenced dossier/blueprint alone) become checkable properties.
- **Extension** — the plugin unit, replacing "a folder in meta-harness you commit to":
  - **Skill** — a capability bundle (SKILL.md + assets) with frontmatter contract (kind, required, depends_on), versioned, registered in an **Extension Registry**. Enable/disable per project from the UI. Situational skills stay lazy.
  - **Integration** — a connector to an external system (GitHub, Plane, Sentry, a product's providers…). "Supported" means: API docs read + a working contract (MCP where available) proven locally against doc-derived fixtures/mocks (Joe, 2026-11-05) — *not* a live production test. Users supply their own credentials at runtime via the secrets store.
  - **Sensor** — a scheduled observer of live systems (perimeter monitoring, quality walks, deploy health) that files findings as Tasks. Sensors run outside the pipeline, always.
  - **Archetype packs, workflow packs, eval packs** — all extensions, all versioned, all installable from a registry (git-backed in v1; OCI/HTTP registry later).
- **Secret** — a reference, never a value, in domain objects: `secret_ref` pointing at the secrets store (OpenBao for us; the Helm chart supports external-secrets / sealed-secrets / plain K8s Secrets for OSS users). The Admin console manages *references, scopes and rotation state*; values never transit the harness API.

### 3.8 Evidence, evals, monitoring
- **Eval** — a named, versioned check with: subject (stage output / chain / whole product), method (`deterministic | agent-judge | human`), criteria, a **mandatory absent-state** (what happens when it cannot run), a **posture** field (`advisory | gating` — default advisory; the standing battery today never gates), and the resource rule from the testing model: **one heavy eval at a time per host, and eval conditions must not manufacture what they measure**. **EvalRun** records verdict on observed evidence only.
- **Scorecard Battery** — today's standing eval instrument, carried over as a first-class Eval pack, with its non-obvious rules intact: scoring is recorded at verify time and is **advisory, never gating**; evidence is assembled mechanically from chain facts; **taste is never machine-graded**; grading supports **source-excluded** mode (the EXP-02 canary measured coupled grading error at 38.9% vs 2.8% source-excluded); and a lone delivery is **unscored until a comparable baseline corpus exists** — which is why §8 now costs evidence/baseline migration instead of discarding history.
- **ThroughputWindow** — the only place “temporal” survives, in the direction Joe named: *looking back*. The ledger aggregates into time windows (hour / day / week, per project / lane / workflow): claims, completions, merges, deploy verdicts, lead time (created → done) and dwell time per state, lane utilisation, hand-back and stall counts. These windows power the dashboards (§6.13) and the daily pipeline record, and they are how sequencing and lane tuning get *evaluated* — e.g. “did raising Loopmentum to 3 slots change completions/week, or just work-in-progress?” Windows are read models over the event ledger, recomputed at will; they store nothing authoritative and gate nothing.
- **Observability export** — monitoring is not the ledger alone: today grading/lifecycle events export via OpenTelemetry (OTLP) to the cluster Collector → SigNoz, with the JSONL ledger as the local record. The reboot keeps that path: the Event Ledger is the source, OTel export is a projection, and SigNoz (or any OTLP backend an OSS user configures) is the external view.
- **Evidence / Ledger** — an append-only event log is the system's spine: every transition, decision, eval verdict, merge, deploy observation is an **Event** (`{ts, actor, object, transition, facts, refs}`). The current ledger (`index.jsonl`) and Plane comments and PR checks all collapse into this. The ledger is queryable via API and UI (trace view, eval grid — both already prototyped in the current control-plane UI and carried over).
- **DecisionLog** — a specialised event stream: every conductor decision (claim / skip / hand-back / merge / stall) with the *inputs it computed from* (policy versions, queue snapshot hash, reason codes). This is what makes "why wasn't X picked up?" a query, not an investigation.
- **Self-heal** — hand-back's owning process (v0 modelled the state but not the process): a handed-back item loses conductor eligibility, gains a self-heal assignment, carries the worker's account of why, and awaits host-access work under the self-heal contract, with re-alerting at 24h dwell. (The current SELF-HEAL.md is itself stale — HARNESS-248 — so the reboot imports the *process*, not the document.)
- **Alert / Finding** — monitoring output: stillness watch (oldest unowned work, oldest logjam, merges/day, owner-pointed-out count → target zero — the Operations God Agent scoreboard, as built-in dashboards), deploy-down detection (a product with no green deploy on current head is DOWN — reported in those words), drift detection (definitions vs live state, plan vs board vs done-vs-live — all projections of one store now, so drift becomes an internal consistency check).

### 3.9 Admin / control plane objects
- **Operator** (user), **RoleBinding** (admin / operator / viewer / agent-service-account), **AuditLog** (every UI/API mutation, who/what/when/before/after), **DeploymentConfig** (the Helm values, reflected into the UI as the Admin console: namespaces, pools, ingress, retention), **Tuning** (lane caps, poll intervals, thresholds — live-editable subset of Policy/Lane config).

Workers remain language-agnostic containers.

**Storage choices (boring on purpose):** Postgres for state + ledger (JSONB for facts), S3-compatible object store for traces/packets/artifacts, K8s Secrets/external-secrets for secret refs. No new database technology. SQLite retires (it was experiment-grade).

GitOps-friendly (Argo CD / Flux compatible — matching our estate-gitops direction). Upgrades = chart version bumps with DB migrations as Jobs. Air-gapped-ish install possible (images + chart only).

## 5. The three hard design questions (answered, not deferred)

### 5.1 Where do definitions live — git or database?
Both, with a strict division: **git is the system of record for *definitions* (workflows, archetypes, skills, policies-as-code, context recipes) — versioned, reviewed, diffable; the database is the system of record for *state* (tasks, chains, events, decisions, eval runs).** A sync controller (in-chart) watches the definitions repo (or bundled chart definitions for OSS single-repo installs) and materialises definitions into the DB as immutable versions; the UI edits definitions by *proposing a change* (creates a PR in git mode, or a new version directly in DB-only mode for small installs — a values flag, defaulting to git mode for teams). Three mechanics v0 asserted but didn't design, now specified: **(a) pinning wins** — a Chain runs the workflow version it started on to completion; a mid-chain definition edit creates a new version that only new chains pick up; **(b) controller-down is an absent state with a named behaviour** — the system keeps running on the last materialised versions, surfaces `definitions: stale` in the console, and refuses *new* definition edits until sync recovers (never a silent wait, per §1.6); **(c) DB-only edits are one-way-exportable** — `harness export` turns DB-mode versions into a git PR, and re-importing that PR is a no-op because versions are content-hashed. Tasks, by contrast, live only in the DB — the register-as-markdown era ends; task *templates* may live in git, task instances never do. This is the end state the 2026-11-02 Plane decision pointed at — Plane's role (state) and meta-harness's role (definitions) each get a proper home, and the sync and its drift class are deleted — but that decision's filings still wait for Joe's go, so this design *proposes* the resolution; it does not presume it.

### 5.2 Plane — include it, fork it, or take its parts? (rewritten v3, grounded)

Facts first (checked 2026-11-06; corrected by the frontier cross-check against the makeplane/plane repo the same day): Plane's Community Edition is **AGPL-3.0-only**, a Django 5.2 + DRF + Celery backend and a React Router v7 (Vite) + MobX frontend (no longer Next.js), shipping as **13 containers** in its self-host bundle (web, admin, space, live, api, worker, beat-worker, migrator, proxy, Postgres, Valkey, RabbitMQ, MinIO) plus ~14 shared packages. It is **open-core**: Plane positions the Community Edition as matching its free cloud tier, while Plane AI and assignable AI agents sit behind paid plans (Pro/Business) under a closed commercial licence with AI-credit metering — our own production Plane runs commercial images (makeplane v3.3.3; that detail is carried from the earlier grounding check, not re-verified in the v3 pass). Stated precisely: the split is *packaging and licence*, not absence of code — the AGPL repo contains an OpenAI-compatible ai-assistant endpoint; what you cannot take is the commercially packaged agent product and its plan-gated surface. Plane Agents (assignable like teammates, @mentionable, triggered by assignment / @mention / work-item events / schedules; “template + playbook” is Plane's own marketing phrasing, and a native MCP server + Agent Development Kit exist) are a tracker feature, not a harness integration (see §3.7b for why that model is rejected for execution regardless of vendor).

Three options:

**A. Include Plane (bundle the unmodified service, harness integrates via its API).**
*For:* the board UX our team already knows, zero board development, work items/cycles/modules/views/pages out of the box.
*Against:* two systems of record to keep reconciled (the exact drift class this reboot exists to kill — mitigated only if Plane is demoted to a projection, at which point its UX is a skin over our objects and its native features (its agents, its automations) become traps that act outside the harness); two consoles for the operator (Plane for tickets, our dashboard for pipeline — the split Joe identified as the missing piece); a second heavy stack (Django/Redis/RabbitMQ + its own upgrade train) inside the Helm chart; and an AGPL service at the heart of a package we intend others to deploy, which constrains our own licence choice (§10 Q4) for the combined work.

**B. Fork Plane and take the parts we want.**
*For:* in theory, keep the work-item/board code, drop the rest.
*Against (decisive):* the parts are not separable — work items are entangled with Plane's Django API, permissions, MobX stores and editor across the monorepo; “taking parts” means adopting most of the monorepo and then maintaining a permanent fork of a fast-moving upstream (Plane ships continuously) — the heaviest possible ownership shape, against §1.10 (boring/finished) and the “system gets lighter as it scales” doctrine. The AGPL cuts both ways: a distributed fork must be published under AGPL, dictating the licence of the combined package. And the fork can only ever take the *Community* parts — the commercial features, including parts of the agent surface, are closed and cannot be taken at all. **Rejected.**

**C. Build the board natively in the harness console; take Plane's concepts, not its code; keep Plane as an optional connector (RECOMMENDED).**
The domain concepts Plane proved — work items with rich properties, cycles (≈ our milestones/sequences), modules, saved views, intake/triage, pages — are *ideas*, adopted freely into §3's objects where they fit. The board itself is a view over harness objects in the same console as the pipeline (§6.0), which is the unification Joe actually wants: Plane never had the pipeline, and bolting our pipeline into Plane's UI (options A/B) means building the hard part inside someone else's frontend anyway. Plane remains supported as an **integration**: during migration our production Plane is a projection (§8), and OSS users who live in Plane can install the connector and project tasks outward — Plane as a window, never as the record, and never as an execution path (its agents are not bound, §3.7b).
*Cost, stated honestly:* we own board UX development. The mitigation is that the dashboard we already have (§6.0) is the nucleus — the read side (runs, chains, traces, evals, queue state) already exists and is the part Plane lacks; the board is comparatively commodity UI over objects we must model regardless.

GitHub Issues and Linear follow the same rule as Plane under all options: integrations/projections, never dependencies, never execution paths.

### 5.3 How do we not lose tunability?
Every constant that today requires a commit + redeploy (lane caps, pickup keys, fix rounds, timeouts, pool cooldowns, stall thresholds) becomes a Policy/Lane/Tuning field, editable in the Admin console, effective on the next conductor decision, audit-logged, and exportable back to git (`harness export` → definitions repo PR) so tuning history stays reviewable. If a knob exists in code as a literal, that's a bug against this design.

## 6. The pane of glass — operator console (UI for everything)

Rule: **if an operator can need it, it is in the UI; if it is in the UI, it is in the API.**

### 6.0 The centre of the console: ticket ↔ pipeline, one surface (added v3)
The prototype already exists and Joe uses it: the control-plane dashboard on the Azure cluster (tailnet: `https://k3s-azure-01.tail0c4aa.ts.net/`). Its lineage is visible in the control-plane source (`ui.html` + API.md): Runs list and run detail, the **trace viewer** (agent invocations/results/prose, with the same shell-read flagging the eval battery applies), the **eval grid** (runs × checks), **Compare** (task × treatment outcomes and cost), the **State view** (queue, per-task transition timelines, audited requeue/cancel), **New request** (sentence → decomposed, validated, queued work), and **Harness auth** (the subscription broker). Stated precisely (frontier correction): the mh **requests and chains** that make a *ticket* drill into its stages, jobs and write-back are **API-level** concepts (API.md) — the experiment console's `ui.html` has no chain view, and there are really **two surfaces** in today's estate: the k3s rig console (this UI) and the product-factory/conductor web surface Joe uses for tickets↔pipeline. The reboot's job is to *merge those two lineages into one console*; v3's wording blended their inventories, and v4 separates them so Phase 2 (§8) is costed as a merge, not a reskin. *(Grounding note: the tailnet dashboard is not reachable directly from the agent VM — checked 2026-11-06, connection fails — so this inventory is from the deployed source lineage and the API/DESIGN record, not a fresh live scrape.)*
**What Plane is missing, in Joe's words, is exactly this connection** — and the reboot's console is designed around it: the board (§6 view 1) and the pipeline are not two tools with links between them. A task's detail *is* its chain: binding (§3.7b), stages, jobs, traces, PR, checks, merge, deploy verdict and eval results, on one page, in one timeline, drawn from the one ledger. Clicking from “ticket” to “what the agent actually did” is zero hops, because they were never separate records. The dashboard is therefore a **core deliverable of Phase 2** (§8), grown from the current UI — not a later polish item, and not a skin over a tracker.

Views (each maps to objects in §3):

1. **Board** — tasks by state/milestone/sequence position. Dragging is defined, not magic: a drag within a milestone rewrites that milestone's explicit `sequence`; a drag across milestones moves the task and appends it to the target milestone's sequence; priority tier is changed from the item, never by dragging. That keeps every board gesture expressible in the PrioritizationPolicy, so the Pickup Preview can always explain the result (derivability, §1.2). Hand-backs and blocks show their mandatory reasons inline.
2. **Pickup Preview** — the derivability view: current queue, computed order, per-item reason codes ("eligible", "blocked: needs X", "held: dependency X not done", "held: parent in backlog", "lane full", "slot held: merging"), next-10-claims simulation. This view alone would have prevented most of the last month's stall investigations.
3. **Chains & Runs** — live stage graph per chain, worker logs, cost/token per stage, stall/escalations with repair history, requeue/cancel (the current state-editor's two audited ops, generalised).
4. **Trace viewer** — paged agent trace with invocation/result/prose filtering (carried from the current UI, it was good).
5. **Eval grid** — runs × checks per task/product, absent-states shown as their own state, never as failures.
6. **Quality** — whole-product walk results, acceptance-lane findings, product DOWN/UP deploy verdicts first (deployment is the process: no green deploy on current head = DOWN, in those words).
7. **Policies** — list, edit (with absent-state and enforcement fields enforced by the form), version history, "what changed" diff, simulate ("would this policy have refused workflow X?").
8. **Lanes & Tuning** — lane caps, pools, conductor config; live edit with audit.
9. **Extensions** — registry browser: skills/workflows/eval packs/integrations/sensors; install, pin version, enable per project.
10. **Context** — recipe viewer: pick project+role+stage, see the exact packet an agent would get, token count, provenance/drift warnings. (The goldfish test, as a button.)
11. **Secrets** — references, scopes, which jobs consumed what, rotation/expiry state. Values never shown, never enterable except through the store's own flow.
12. **Admin** — users/roles, deployment config (Helm values reflected), audit log, system health, backup/restore.
13. **Dashboards** — the God-Agent scoreboard: oldest unowned work, oldest logjam, merges/day per product, owner-pointed-out count; daily pipeline record (what shipped, what did not, what blocked) generated from the ledger — no hand-written status ever again.

## 7. APIs for agents (everything, for agents)

- **REST/JSON + OpenAPI** as the contract; generated clients; the same API the UI uses.
- **MCP server** exposing the harness as tools (create task, claim context packet, submit stage result, file finding, run eval, read decision log…) — agents are first-class citizens, and our own Juno/Hermes/personas consume the harness this way.
- **Service accounts** with scoped tokens per role, with an explicit permission matrix as part of the design (v0 asserted scoping in one sentence; the matrix *is* the design): a **build worker** can read its own context packet and submit its own stage result — nothing else (today's workers can do exactly one thing, and the reboot keeps that bar); a **sensor** can file findings/tasks in its project and nothing else; a **grooming agent** can create/groom tasks but never claim or merge; the **conductor** service account is the only one that can claim, hand back, or instruct the Integrator; **operator** accounts are the only ones that can edit Policies/Lanes or answer Decisions. No token may create tasks *and* claim them — that combination is the queue-poisoning vector and is refused at token-issuance.
- **Webhooks/events out** — every ledger event can stream (SSE/websocket + webhook subscriptions) so external agents (perimeter monitoring, A2A mesh) react without polling.
- **CLI** (`harnessctl`) — a thin API client for humans/scripts; everything the CLI does is an API call (no back doors).

## 11. Open source is the ideation engine (added 2026-11-06, Joe)

Joe's reason for open-sourcing, in his words: *"i want people to use it and throw their agents at it and improve it in ways i never thought of. ideation has been a weak point here."* That makes open source a **design requirement from the first release, not a Phase 6 publishing step** — the community (and their agents) is the ideation flywheel this project has been missing, and the system must be shaped so that flywheel can actually turn:

1. **Small core, everything else an extension.** The surest way to be improved in ways we never thought of is to make the un-thought-of thing *installable without our permission*: workflows, skills, integrations, eval packs, archetypes, sensors and personas all ship through the Extension Registry (§3.7), with a stable, versioned extension API. Core changes are the rare path; extensions are the normal path.
2. **Agent-legible by construction.** People will throw *their agents* at it — so the repo must be operable by a zero-context agent: an `AGENTS.md` that actually suffices, machine-readable specs (OpenAPI, JSON schemas for every domain object), the goldfish install test (§8 Phase 6) run in CI, worked examples, and seed tasks labelled for agents. If a competent agent cannot install it, run the demo workflow, and land a small extension unaided, the release is not done — that is a release gate, not documentation polish.
   **Honesty note (frontier check, 2026-11-06): the v3 design does not yet fully back this.** Three first-class pieces are now added to scope, and until they exist §11's claim is a goal Phase 6 must *build toward*, not a property the design already has:
   - a **contributor ContextRecipe** — the repo brief, architecture map, one-command local replica (the zero-difference doctrine applied to *our own* codebase), and self-check evals a foreign agent can run to verify its own change before submitting;
   - an **extension SDK** — scaffold/template, conformance test kit, and an API-stability/versioning commitment, plus an RFC path (a Proposal, §11.4) for proposing a *fifth* extension kind, since a genuinely novel idea currently has no home shorter than forking core;
   - a **fork-PR verification lane** — how an external PR gets verified: sandboxed CI that can run strangers' code *without* estate runners (the standing no-GitHub-hosted-runners rule is about our own work; running untrusted fork code needs its own explicitly isolated story), the merge contract (tests, DCO sign-off, review expectations), and who runs the adversary review. Unspecified verification is where community ideation goes to die — at the maintainer's desk.
3. **Contributions are bound and verified, like everything else.** An agent-contributed change enters through the same machinery: a task, a bound execution (§3.7b), the battery/evals as the merge bar, the fenced integrator. That is what makes "throw your agents at it" safe to invite — the harness can accept agent labour at scale because it never has to trust it, only verify it. (For the upstream project this is also the demo: the harness develops itself, in public, with its own trains.)
4. **Ideation has a front door.** Ideas arrive as **Proposals** (an RFC-shaped Task type): problem, proposed shape, smallest experiment. Proposals are groomed like everything else — duplicates merged, promising ones turned into spikes with eval criteria — and the public roadmap is a projection of the real board, not a marketing page. Unexpected uses are harvested, not just welcomed: the console/registry makes it one click to publish a workflow or recipe you built back to the registry, with attribution.
5. **Licence serves the goal.** The goal is adoption + contribution, which points permissive — and the frontier checker's licence assessment (in `NAME-AND-V3-CHECK.md`) lands firmly: **Apache-2.0** (permissive + express patent grant; the default licence of the Kubernetes/Helm ecosystem this ships into; AGPL rejected for the same reasons §5.2 documents in Plane — it would chill exactly the experimentation loop Joe wants; MIT an acceptable second). Control is kept where it belongs: licence the *code* Apache-2.0, protect the *name/logo as trademark*. Contribution mechanics matter as much as the licence: **DCO sign-off, not a CLA** (a CLA is a signature round-trip that drive-by humans skip and agents cannot complete), and a decision now *against* preserving dual-licensing, since that requires a CLA and taxes the unsolicited contributions the project exists to attract. Final licence call is Joe's (§10 Q4). Governance legibility ships with it: a named maintainer model, a public roadmap (a projection of the real board, §11.4), and refused ideas recorded *with their reasons* — Decision objects projected publicly — because strangers ideate where they can see what is wanted and what was refused, and why.
6. **What we keep back is nothing structural.** No open-core split where the good parts are closed: the split that killed forkability in Plane (§5.2) is the anti-pattern. If NonceLogic later sells anything, it sells hosting, support and our own hosted personas — services around the system, not withheld pieces of it.
